## [0.9.3] — 2026-10-09

### Исправлено
- **ДЕДЛОК RRP-сессии (found-by-test, гонялся только под -race)** — `Session.handle` для кадра Close вызывал `stream.markClosed` под `s.mu`, а `stream.Read` держит `st.mu` и берёт `s.mu` (учёт outstand) → классический AB-BA: многопоточная закачка могла зависнуть сессию намертво. Канон порядка блокировок: `st.mu → s.mu` и никогда наоборот; markClosed вынесен из-под `s.mu` (идемпотентен).
- **Канон flow-control: кредит телефона ≤ буферу приёма.** Раньше сервер раздавал `tunnel_window = StreamWindow×4` (2 МБ) при буфере DATA на стрим 1 МБ: клиент с окном больше буфера при медленном читателе убивал стрим анти-абьюзом (`close(4)`) и рвал закачку. Теперь кредит `StreamWindow×2` = ровно буфер — честный клиент (Kotlin Semaphore) буфер исчерпать не может.
- fake-phone в e2e-тестах уважает flow-control как настоящий APK (per-stream кредит из READY + пополнение по WINDOW) — тесты теперь репрезентативны к реальному клиенту.

### Добавлено
- **Скриншот-роботы разделены на два ПОЛНОСТЬЮ независимых воркфлоу** — `screenshot-apk.yml` (эмулятор) и `screenshot-web.yml` (веб-панель из опубликованного образа): раздельные расписания/триггеры/concurrency, каждый коммитит только свой ассет; фейл одного не влияет ни на релиз, ни на второй робот.
- **Тест многоканальности** (`TestMultiStreamThroughput`): 8 параллельных потоков через одну сессию, SHA-256 каждого потока, ноль подмен/потерь; агрегат гейтится от коллапса, скорость — честная метрика в логе.
- prodprobe: `-proto mtproto2` — DH-апгрейд против прода той же функцией, что и APK (KEY_REQ→KEY_RESP, IGE); `-streams N` — параллельные PROBE (многоканальность одной сессией).

### Улучшено
- **Кнопка Старт — канон анимаций 2026**: тактильный отклик нажатия (сжатие 3% + упругий Overshoot-возврат), мягкий «поп» при смене состояния, кольца состояния переписаны на `PulseRingView` — подключение: indeterminate-дуга с «дышащим» размахом; подключено: двойное кольцо-дыхание со сдвигом фазы π; аниматор не крутится, когда вью невидимо (экономия батареи). Всё на API 14+ (ValueAnimator+Canvas).
- Версия APK под именем приложения на главной (техническая метка, без строковых ресурсов).

### Для разработчиков
- Тестов: 137 Go + 187 JVM.
- CI-воркфлоу: `screenshot.yml` → `screenshot-apk.yml` + `screenshot-web.yml`.

- Keepalive адаптивен к фактическому RTT (20–55 с вместо фиксированных 60 с).

## [0.9.0] — 2026-10-09

### Исправлено
- **КОРЕНЬ прод-инцидента «TLS bad_certificate(42)» после апгрейда 0.8.3**:
  клиент считал пин от ЛИСТА цепочки (chain[0]), сервер и все ссылки — от CA
  (последний серт). Плановая ротация листа при деплое 0.8.3 меняла хэш листа →
  честные ссылки падали с ложным «CA-pin НЕ совпал». Теперь клиент хеширует
  ПОСЛЕДНИЙ серт цепочки (CA) — канон един для обеих сторон; ссылки менять
  НЕ нужно, они остаются валидными при любой ротации листа.
  KAT-тест RrpPinTest: [leaf, CA] → пин от CA; ротация листа не меняет пин.
  Диагностировано живой телефонной ролью против прода 81.25.59.194:4433
  (TLS+pin → READY → PONG → PROBE OK) — сервер v0.8.3 полностью здоров.

### Добавлено
- **Ротация CA — ЯВНОЕ подтверждение владельца (v0.9.0)**: при настоящей
  смене CA сервера APK показывает диалог «Сервер сменил сертификат» с фактическим
  пином в каноне ссылки (base64url) — «Принять новый пин» обновляет ссылку
  (RrpUri.replacePin: parse→copy→serialize, остальные поля байт-в-байт),
  пишет в журнал и реконнектит. Анти-MITM канон усилен: молча не доверяем
  НИКОГДА, теперь и явное принятие — один тап владельца вместо ручного re-enroll.
- **cmd/prodprobe** (Go): телефонная роль для диагностики боевого сервера —
  TLS+SPKI-pin → HELLO/AUTH/READY → PING/PONG → PROBE (проверяет и egress
  при подключённом телефоне). Токен только через env/флаг, ничего не хранит.

### Изменено
- «реальный pin» в журнале и диалоге теперь в каноне ссылки (base64url без
  паддинга) — можно вставить в rrp:// как есть;
- screenshot-воркфлоу: явный `shell: bash` (dash не парсит циклы скрипта);
- тестов: 131 Go + 182 JVM (+6: RrpPin KAT, replacePin).

## [0.8.1] — 2026-10-08

### Безопасность (анти-MITM и честная PKI)
- **Строгий SPKI-pin (анти-MITM)**: если pin в ссылке ЗАДАН и сервер
  предъявил другой сертификат — клиент ОТКЛОНЯЕТ соединение с внятной
  ошибкой и реальным pin в журнале (иначе это MITM или смена CA → re-enroll).
  TOFU остался только для первой «дружбы» (пина в ссылке нет) и явного
  override `trustSelfSigned=true`. Чужим сертификатам клиент больше не
  доверяет по умолчанию.
- **Серты живут годами**: leaf-сертификат сервера — **3 года** (было 90 дней),
  перевыпуск ЗАРАНЕЕ за 90 дней до конца срока; ротация листа по-прежнему
  не ломает клиентов (пин — SPKI CA). Старые короткие листы мигрируют на
  длинные при первом рестарте.
- **SAN сертификата — и IP, и DNS-имя**: `listen.public_host` (DDNS) и все
  `listen.tls_hosts` попадают в лист — коннект по DNS-имени сервера
  равноправен коннекту по IP.
- **Верификация APK при обновлении (анти-подмена)**: апдейтер сверяет
  скачанный APK с `SHA256SUMS` релиза; несовпадение → установка отменяется.
- **HTTPS-гейт в privacy-audit**: plaintext `http://` в коде разрешён
  только loopback/шаблоны LAN (healthcheck, admin-инбокс) — всё остальное
  только `https://`.

### Добавлено
- **Версии протоколов — по всему стеку (v0.8.1)**: у каждого протокола
  реестра появилась публичная версия (`ver` в `modules.json`: rrp1 = «1»,
  mtproto2 = «2.0») и метка (`name`). Они пробрасываются ВЕЗДЕ: строки
  статуса и логи клиента (`RECV READY … proto=mtproto2 (MTProto/2 (v2.0))`),
  переключатель протоколов в APK, «О приложении» (+ строка «Версия
  протокола»), веб-морда `/ui` (сессии и подзаголовок) и `/status`
  (`protocol_labels`/`protocol_vers`), логи сервера (`proto_label`).
  Новый протокол обязан нести версию в манифесте; если публичной версии
  в природе нет — поле пустое, и тогда нигде ничего не показывается.
- **Клиентский фоллбек модулей протоколов**: если новый протокол-модуль
  ломает подключение (3 неудачи подряд), клиент ОТКАТЫВАЕТСЯ на предыдущий
  рабочий (`rrp1`) и честно пишет причину в журнал. Сервер НЕ откатывается
  никогда (анти-цикл: обновления APK/сервера рассинхронизированы, авто-
  обновление может быть отключено — модули заморожены, и это не ломает

  В compose публикуется 1080/udp; SSRF-guard действует (порт 53 — разрешён).
- **WebSocket-транспорт RRP** (`transport=ws`): тот же TLS-порт 4433, апгрейд
  RFC 6455 `/rrp` — обход DPI-ограничений портов (443/80/CDN). Сырой RRP/1
  работает как раньше, один порт обслуживает оба транспорта.
- **График трафика в приложении**: реалтайм (байт/с, окно 60 с) в статус-карточке.
- **Экспорт/импорт конфигурации файлом** (SAF, API 19+; на 14–18 скрыто).
- **Деплой одной командой из любого каталога**: `deploy/install.sh` создаёт
  `./reverseray/` (compose + state + .env + инструкция) относительно текущей папки.
- Rate-limit рукопожатий смягчён: 120/мин/IP (было 60), настраивается
  `RR_LIMITS_HANDSHAKES_PER_MIN`; lockout остался только за невалидный HMAC.
- CI: gitleaks-скан секретов, dependency-review для PR, валидация gradle-wrapper.

### Исправлено
- **«no such algorithm: SHA-512 for provider BC» навсегда**: TLS-крипто клиента
  переведено на BcTlsCrypto (lightweight, без JCA) — больше не зависит от
  урезанного платформенного провайдера "BC". Работает из коробки на всех
  Android 4.0+ (API 14+), включая те, где v0.5.1 не помогала.
- Гонка close/send в UDP-канале сессии (обнаружено race-детектором в тестах).
- Ответ SOCKS5-клиенту в UDP дополняется SOCKS-заголовком [RSV/FRAG] (RFC 1928).

### Производительность
- Release-пайплайн: паблиш больше не пересобирает бинарии (артефакты вместо
  дубль-сборки) — минус 3 джобы и ~5–8 минут на релиз.
- CI: Go-тесты и coverage в одном прогоне; кэш Gradle (`setup-gradle`);
  `concurrency: cancel-in-progress`; gradle build-cache/parallel.

### Изменено (UI)
- Главная кнопка **«Старт» — большая круглая (220dp), сверху**, под ней «Стоп»;
  шапка экрана — иконка приложения (баннер-заглушка убран).

## [0.3.1] — 2026-09-20

### Исправлено
- **APK из релиза не устанавливался**: публиковалась неподписанная сборка
  (`app-release-unsigned.apk`), Android отвергал её при установке.
  Теперь релизный APK подписан репозиторным ключом (v1+v2+v3 схемы) и
  устанавливается штатно на Android 4.0–16; обновления ставятся поверх
  предыдущих благодаря стабильной подписи.

### Безопасность
- Подпись APK: приоритет — секреты окружения (`RR_KEYSTORE*`); при их
  отсутствии используется открытый репозиторный ключ
  (`android/app/rr-release.keystore` + `signing.properties`).
  Он обеспечивает стабильность подписи, но не авторство: подлинность
  артефактов верифицируется по `SHA256SUMS` в GitHub Release.
- Владельцы, желающие публиковать APK под личным ключом, задают
  `RR_KEYSTORE*` в Secrets — подпись переключается автоматически.
