# Buffer/2 — LEDGER + ACK: дозылка при потере транспорта (v1.9.8)

Дополнение к канону Buffer/1 (`docs/spec/buffer.md`). Buffer/1 покрывает
только «неотправленное» (MODE_FAIL на клиенте, буфер c→p на сервере).
Buffer/2 закрывает потерю **отправленного, но не подтверждённого**: байты,
которые ушли в outq старой сессии (или в ядро мёртвого сокета) и погибли
вместе с ней. При смерти транспорта рвалось ровно это окно — браузер
зависал (p→c) или связь с целью терялась (c→p).

Канон самодостаточен: меняешь — обновляй ОБЕ стороны
(`server/internal/buf/ledger.go` + `android/.../core/RrpAckLedger.kt`).

## Принцип

У каждого стрима свой **октетный счётчик от отправителя** (c→p и p→c —
два независимых пространства смещений). Отправитель ведёт **LEDGER** —
список отправленных и не подтверждённых чанков; получатель шлёт
**кумулятивный ACK** по фактически доставленным байтам. При потере
транспорта и повторном открытии стрима (OPEN_RESUME, Buffer/1) отправитель
**досылает** необработанный хвост из LEDGER, затем живёт обычным образом.

- **Не подтверждённое = потерянное**: ACK не пришёл → чанк остаётся в
  LEDGER и досылается. Ноль потерь.
- **Подтверждённое = не досылается**: ACK пришёл → чанк выкинут из LEDGER.
  Ноль дублей (получатель игнорирует оффсеты ниже своей базы).
- **Порядок**: транспорт in-order; досылка строго в порядке оффсетов,
  до новых байтов.

## Согласование

- Клиент объявляет HELLO caps **`stream-ack`**; сервер отвечает
  READY features **`stream-ack`**. Активен только когда заявили ОБА.
- Старые клиенты/серверы: кадр DATA без префикса, ACK/расширенный
  OPEN_OK не используются — поведение Buffer/1 (v1.9.6) сохранено.

## Форматы кадров (добавка к RRP/1)

| Кадр | Направление | Payload |
|---|---|---|
| `TypeAck = 0x2F` | S→C | `[u64be offset]` — кумулятивно доставлено (p→c) |
| DATA (ack-режим) | обе | `[u64be offset][payload]` |
| OPEN_OK (resume, ack-режим) | C→S | `[u8 err_code=0][u64be K]`, K = потреблено телефоном (c→p) |

Префикс оффсета живёт ВНУТРИ крипто-конверта (шифруется как payload).
`MAX_DATA_PAYLOAD` не меняется: чанк ≤ 65535-8. ACK ≤ 8 байт
(лимит контрольных кадров покрывает).

## Семантика сторон

**Сервер, направление c→p (отправитель):**
- `stream.Write` (ack-режим): чанк копируется в LEDGER, оффсет назначает
  LEDGER (для resume-стрима база = K из OPEN_OK), затем чанк с префиксом
  уходит в outq.
- WINDOW от телефона (потребление c→p) — честная сумма потреблённого:
  `ackOut += inc; ledger.EvictTo(ackOut)` (автотюн-рост сюда не входит —
  рост ходит только в WINDOW S→C).
- При паркинге (StreamError 1): LEDGER-снимок уходит в `park.Parked.replay`,
  живые байты браузера продолжают копиться в буфере (Buffer/1).
- При RESUME: телефон в OPEN_OK присылает K; hub отфильтровывает replay
  (чанки с концом ≤ K — телефон их уже получил), остаток дозылается через
  `stream.Write` СНАЧАЛА, потом подключается буфер (FIFO+live).

**Телефон, направление c→p (получатель):**
- DATA: чанк с оффсетом пишется в целевой сокет; дубль
  (`off+len ≤ consumedTotal`) — скип; гэп — дроп с журналом.
- Потребление копится абсолютно (`consumedTotal`, переживает resume через
  ParkedSock), кумулятивный ack уходит серверу в WINDOW-порциях
  (как и раньше) и K в OPEN_OK при resume.

**Телефон, направление p→c (отправитель):**
- `pumpOutgoing` (ack-режим): сначала досыл LEDGER (отправленное-но-не-
  ACKнутое, те же оффсеты — сервер-читатель дропает `off+len ≤ baseIn`,
  дубли безопасны), затем живое чтение. outBuf (Buffer/1) в ack-режиме
  не используется.
- Чанк → LEDGER **до** отправки (оффсет назначает LEDGER, `next += n`);
  MODE_FAIL не теряет чанк — он остаётся в LEDGER и досылается при
  следующем OPEN_RESUME (сервер-зеркало делает так же: Append в
  `stream.Write` до постановки в outq).
- ACK от сервера: `ackedOffset = max(...); evict ≤`.
- LEDGER переживает паркинг: `ParkedSock(socket, parkedAt, consumedTotal,
  ledger)`; при resume новый стрим наследует LEDGER (оффсеты продолжаются).
- При resume: сервер сразу шлёт `ACK(baseIn)` (baseIn = доставлено
  браузеру до смерти, из `park.Parked.delivered`); телефон выкидывает
  подтверждённое и досылает хвост. Приемник (сервер) дропает чанки с
  `off+len ≤ baseIn` — они уже у браузера.

**Сервер, направление p→c (получатель):**
- `stream.Read` (доставка браузеру): `delivered += n`; порог 16 КиБ →
  кумулятивный `TypeAck(delivered)`. WINDOW S→C не меняется (flow-control).
- При паркинге: `delivered` сохраняется в `park.Parked.delivered`;
  непрочитанный inQ умирает со старой сессией — телефон досылает его как
  неподтверждённый (ACK был только за доставленное). Потерь нет.

## Границы

- LEDGER обеих сторон ограничен окном потока (permits): неподтверждённых
  байт не больше, чем выдано кредитов (+ outBuf ≤ 256 КиБ по Buffer/1).
- TTL паркинга против ТСПУ-пауз: сервер `limits.stream_park_sec` (дефолт
  120 с), телефон `STREAM_PARK_MS = 120_000` — согласованы.
- UDP-релей Buffer/2 не касается (дейтаграммы не ретранслируются).
- TCP-соксеты туннеля против ТСПУ-тихой смерти: keepalive 15/5/6,
  `TCP_USER_TIMEOUT = 45s` (= IDLE + INTVL×CNT, канон Cloudflare),
  `TCP_NOTSENT_LOWAT = 128 КиБ` (недоставленное держится в LEDGER,
  не в ядре). Best-effort, Linux-only, ошибки тихо.

## KAT (обе стороны, одинаковые векторы)

```
append("0011") → off 0; append("2233") → off 2; append("445566") → off 4
snapshot → base=0, chunks=["0011","2233","445566"]
evictTo(5)     → base=5, chunks=["5566"]          (голова "445566" подрезана)
evictTo(7)     → base=7, chunks=[]
evictTo(2)     → без изменений (назад не отматываем)
```

Replay-фильтр при RESUME (клиентский K): сцена snapshot выше, K=5 →
`"445566"`[1:] → досылается `"5566"`; K=7 → досылать нечего.
