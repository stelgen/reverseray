# Buffer/1 — канон базовой буферизации стримов

ЕДИНЫЙ источник истины для буферизации payload-потоков RRP. Один этот файл
задаёт семантику и константы; реализации-зеркала (Go и Kotlin) обязаны вести
себя одинаково и проверяются кросс-языковыми KAT-векторами (конвенция канона:
«Меняешь канон — обновляй векторы и ОБЕ стороны»).

## Место в стеке

Буфер живёт на слое стримов — НИЖЕ конверта (crypto/envelope) и ВЫШЕ
транспорта (TCP/WS). Буфер не знает и не может знать текущий протокол
(rrp1 / mtproto2 / wireguard / bittorrent / apimask / будущие): смене
протокола соответствует реконнект, а буферы переживают реконнект — поэтому
правила должны выполняться для ЛЮБОГО протокола, и новый протокол наследует
поведение автоматически.

## Задача

- Нулевая потеря: байт, принятый от приложения и не ушедший в мёртвый
  транспорт, дропаться не имеет права — он досылается после RESUME.
- Backpressure: при переполнении буфера давление передаётся производителю
  (TCP), а не буферизации дропами.
- Порядок: FIFO. Байты, накопленные до RESUME, идут первыми.

## Константы канона

| Константа | Значение | Смысл |
|---|---|---|
| `CAP` | 262144 | верхняя граница буфера, байт (256 КиБ; бывший park.PendingCap) |
| `MAX_CHUNK` | 16384 | максимальный чанк одного push, байт (16 КиБ) |

## Состояние ядра

FIFO-очередь из чанков (копий `ByteArray`/`[]byte`), `n` — суммарная длина,
`cap = CAP`, необязательный `sink` (живой стрим после Attach), флаг `closed`.

## Операции (семантика)

- `push(chunk) -> ok` — добавляет КОПИЮ чанка в хвост. Если `sink` задан —
  пишет напрямую в sink (живой путь, мимо буфера). Если `n+len > cap`:
  * MODE_BLOCK (сервер, c→p, много производителей): блокируется до появления
    места, Attach или Close (TCP backpressure);
  * MODE_FAIL (клиент, p→c, один производитель — pump): возвращает `false`.
  Если закрыт — `false`/ошибка, данные не принимаются.
- `attach(sink) -> err` — досылает FIFO-буфер в sink (по порядку), затем
  переводит push на живой путь. Ошибка записи → буфер закрывается.
- `poll() -> chunk?` — извлекает чанк из головы (MODE_FAIL-клиент).
- `pushFront(chunk)` — возвращает чанк в голову (повторная попытка).
- `len() -> int`, `live() -> bool` (sink задан), `closed() -> bool`, `close()`.

## Интеграция (обязательные точки)

1. Сервер c→p: `park.Parked` владеет `buf.Buffer` (MODE_BLOCK);
   `park.Feed` = `push`, `park.Resume(st)` = `attach(st)`.
2. Клиент p→c: `RrpClient.Stream.outBuf` (`RrpStreamBuffer`, MODE_FAIL).
   `pumpOutgoing`: при ошибке `sendFrame` прочитанный чанк → `push` (не
   теряется); при OPEN_RESUME — досыл `poll → sendFrame` ДО новых чтений
   из сокета; при повторной ошибке чанк возвращается `pushFront`.

## Границы базовой модели

Байты, уже отданные в мёртвый транспорт (ушли в wire до смерти соединения),
считаются потерянными: восстановить их без ACK/последовательных номеров
невозможно. Разбор последовательностей с ACK-резюмированием — отдельная
эволюция канона (новый файл-спека, не правка этой).
